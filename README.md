### Вопрос №1.01. Проверка пустой ссылки через функцию ЗначениеЗаполнено()
* **Суть платформенного механизма:** В платформе 1С пустая ссылка (например, `Справочники.Номенклатура.ПустаяСсылка()`) — это не `Неопределено` и не `Null`. Это полноценное валидное значение ссылочного типа, состоящее из нулевого уникального идентификатора (00000000-0000-0000-0000-000000000000). Системная функция `ЗначениеЗаполнено()` спроектирована так, что она распознает пустую ссылку любого типа и возвращает для неё `Ложь`.
* **Что проверяем на практике:** Проверяем пустую ссылку справочника с помощью `ЗначениеЗаполнено()`, а также сравниваем её с `Неопределено`, чтобы зафиксировать разницу в поведении системы.

### Вопрос №1.02. Поведение значений NULL при логических операциях сравнения в запросах
* **Суть платформенного механизма:** В языке запросов 1С:Предприятия значение `NULL` подчиняется правилам трехзначной логики SQL (истинного отсутствия данных). Любое прямое сравнение значения `NULL` с помощью стандартных математических операторов (`=`, `<>`, `<`, `>`), даже с самим собой (`NULL = NULL`), принципиально возвращает результат `Ложь` (точнее, `Unknown`, который трактуется как `Ложь`). Для корректного определения пустого SQL-поля (например, при левом соединении) платформа требует использовать специализированный унарный оператор `ЕСТЬ NULL`.
* **Что проверяем на практике:** Выполняем SQL-запрос к справочнику, вычисляя выражения `NULL = NULL` и `NULL ЕСТЬ NULL` внутри конструкции `ВЫБОР`. Доказываем разницу в логике СУБД.


### Вопрос №1.03. Особенности неявного приведения типов при сложении в языке BSL
* **Суть платформенного механизма:** В программном коде 1С тип результирующего выражения при использовании оператора сложения `+` жестко определяется типом **первого (левого)** операнда. Если левый операнд имеет тип `Строка`, платформа выполняет конкатенацию, приводя правый операнд к строке. Если левый операнд имеет тип `Число`, платформа пытается выполнить математическое сложение, принудительно преобразуя правый операнд к числу. Если правая строка содержит нецифровые символы, система генерирует неустранимое исключение времени выполнения (Runtime Error) «Преобразование значения к типу Число не может быть выполнено».
* **Что проверяем на практике:** Поочередно складываем строку с числом и число со строкой (включая невалидную текстовую строку), перехватывая системную ошибку типизации через блок `Попытка...Исключение`.


### Вопрос №1.04. Особенности типизации и логика «Пустой ссылки» составного типа в запросах
* **Суть платформенного механизма:** Когда реквизит имеет составной тип, СУБД хранит его в нескольких физических полях: поле «Тип» и поле «Идентификатор». Если реквизит не заполнен, его значение в базе равно специальной пустой ссылке конкретного типа (или `Неопределено`, если тип еще не выбран). В языке запросов 1С конструкция `Реквизит ЕСТЬ NULL` вернет `Ложь` для незаполненного составного поля, потому что там физически лежит пустая ссылка, а не `NULL`. Чтобы проверить составное поле на «пустоту» в запросе, нужно использовать конструкцию `Реквизит = ЗНАЧЕНИЕ(Справочник.ИмяСправочника.ПустаяСсылка)`.
* **Что проверяем на практике:** Добавим в нашу обработку запрос, который проверяет незаполненный реквизит составного типа. Сравним поведение условий `ЕСТЬ NULL` и `= ЗНАЧЕНИЕ(...)`, чтобы наглядно увидеть разницу.


### Вопрос №1.05. Поведение виртуальных таблиц при использовании условий ГДЕ вместо параметров
* **Суть платформенного механизма:** При работе с виртуальными таблицами (например, `СрезПоследних`, `Обороты`) платформа 1С генерирует подзапросы к СУБД. Если условие (например, по номенклатуре) передано в параметры самой виртуальной таблицы, платформа накладывает фильтр на самом раннем этапе выборки данных в подзапросе СУБД. Если же фильтр наложен в секции `ГДЕ` итогового запроса, СУБД сначала выберет абсолютно все записи из базы (вычислит итоги или срез для терабайта данных), построит огромную временную таблицу и только потом отсечет лишнее. Это приводит к критическому падению производительности и избыточной нагрузке на дисковую подсистему и память.
* **Что проверяем на практике:** Напишем два запроса к несуществующему регистру (или сымитируем обращение через синтаксический анализ), чтобы зафиксировать правильный синтаксис передачи параметров фильтрации вглубь виртуальной таблицы.


### Вопрос №1.06. Разница между ссылочными и объектными типами при изменении данных в базе
* **Суть платформенного механизма:** В 1С важно разделять легковесные ссылки (`СправочникСсылка`) и тяжелые объектные типы (`СправочникОбъект`). Ссылка — это просто UUID, она не хранит в себе данные реквизитов и не блокирует базу. Чтобы изменить данные, необходимо получить объект методом `ПолучитьОбъект()`, который считывает всю запись из СУБД в память и накладывает оптимистическую (или пессимистическую) блокировку. Запись данных всегда происходит только через объект методом `Записать()`. Попытка изменить реквизит напрямую у ссылки вызовет ошибку компиляции или выполнения, так как ссылка доступна только для чтения.
* **Что проверяем на практике:** Попробуем программно изменить реквизит у ссылки, перехватим ошибку платформы через блок `Попытка...Исключение` и покажем правильный способ модификации данных через получение объекта.


### Вопрос №1.07. Поведение транзакций при использовании оператора Попытка...Исключение
* **Суть платформенного механизма:** В платформе 1С любая ошибка уровня СУБД (например, нарушение уникальности индексов базы данных) внутри транзакции безвозвратно переводит её в состояние сбоя (Transaction Doomed). Конструкция `Попытка...Исключение` в коде BSL позволяет перехватить эту ошибку, чтобы сеанс пользователя не завершился аварийно, но она **не способна спасти транзакцию**. Блокировка и состояние сбоя фиксируются на уровне СУБД. Любая последующая попытка вызвать `ЗафиксироватьТранзакцию()` гарантированно вызовет критическое исключение: «Транзакция активна, но её выполнение невозможно».
* **Что проверяем на практике:** Открываем транзакцию и внутри блока `Попытка` намеренно создаем два элемента справочника с одинаковым кодом, вызывая ошибку уникальности СУБД. Перехватываем её и доказываем, что транзакцию после этого зафиксировать уже невозможно.


### Вопрос №1.08. Поведение параметров ЗаполнитьЗначенияСвойств() при несовпадении типов
* **Суть платформенного механизма:** Встроенная функция `ЗаполнитьЗначенияСвойств()` осуществляет копирование данных между реквизитами разных объектов по совпадению их имён. Однако, если имена свойств совпадают, но их типы принципиально различны (например, в источнике лежит `Строка`, а в приемнике — `Число`), платформа производит попытку неявного приведения типов. Если приведение невозможно, система не генерирует ошибку времени выполнения (Runtime Error) и не прерывает код, а просто тихо игнорирует данное свойство, оставляя значение в приемнике неизменным. Это поведение критически важно учитывать при написании универсальных механизмов обмена данными, чтобы не допускать скрытой потери данных.
* **Что проверяем на практике:** Создадим структуру-источник со свойством типа `Строка` и структуру-приемник с таким же именем свойства, но типа `Число`. Выполним копирование и зафиксируем, как платформа предотвращает аварийное завершение потока и сохраняет исходное значение приемника.

### Вопрос №1.09. Поведение индексов во временных таблицах при оптимизации сложных запросов
* **Суть платформенного механизма:** Когда в запросе создается временная таблица (`ПОМЕСТИТЬ ВТ_Данные`), СУБД физически создает реальную таблицу в базе данных `tempdb`. Если эта таблица в дальнейшем соединяется с другими таблицами по определенным полям (например, по ссылке), СУБД вынуждена выполнять полное сканирование (`Table Scan`), что критически снижает скорость при объемах более нескольких сотен строк. Конструкция `ИНДЕКСИРОВАТЬ ПО Поле` принудительно создает индекс в СУБД для этой временной таблицы. Это позволяет оптимизатору использовать высокоскоростной поиск (`Index Seek`) вместо сканирования, сокращая время выполнения запроса в десятки раз.
* **Что проверяем на практике:** Создадим пакетный запрос с временной таблицей, содержащей индексацию, и зафиксируем синтаксическую корректность конструкции для оптимизации планов запросов СУБД.

### Вопрос №1.10. Разница между методами Прочитать() и ПолучитьОбъект() при оптимизации памяти
* **Суть платформенного механизма:** Когда необходимо обновить данные уже существующего в памяти объекта (`СправочникОбъект`), вызов метода `Ссылка.ПолучитьОбъект()` заставляет платформу уничтожить старый объект, выделить память под новый экземпляр, повторно считать все реквизиты из СУБД и заново инициализировать механизмы блокировки. Специализированный метод `Объект.Прочитать()` работает иначе: он не пересоздает объект в памяти, а просто обновляет значения его текущих реквизитов напрямую из базы данных. Это исключает лишние аллокации в оперативной памяти и снижает нагрузку на сборщик мусора.
* **Что проверяем на практике:** Создадим элемент справочника, изменим его свойства в памяти и поочередно применим оба метода. Через операторы сравнения докажем, что `ПолучитьОбъект()` создает новый объект в памяти, а `Прочитать()` обновляет текущий.


### Вопрос №1.11. Особенности генерации внутренних адресов через ПолучитьНавигационнуюСсылку()
* **Суть платформенного механизма:** Метод `ПолучитьНавигационнуюСсылку()` преобразует внутренний идентификатор объекта 1С в текстовую строку унифицированного формата (`e1cib/data/...`). Сама по себе эта строка не содержит сетевого адреса. Для использования ссылки в веб-клиенте или отправки внешним пользователям её необходимо объединить с адресом публикации информационной базы. Адрес публикации извлекается из функции `СтрокаСоединенияИнформационнойБазы()`. При парсинге этой строки платформа позволяет определить режим работы (файловый `File=` или клиент-серверный `Srvr=`) и сформировать валидный HTTP-URL для браузера.
* **Что проверяем на практике:** Получаем внутреннюю ссылку объекта, анализируем строку соединения информационной базы, определяем режим работы системы и собираем внешнюю веб-ссылку для открытия элемента через браузер.

### Вопрос №1.12. Особенности использования конструкции ЗНАЧЕНИЕ() для предопределенных элементов в запросах
* **Суть платформенного механизма:** В языке запросов 1С для получения ссылки на предопределенный элемент справочника, перечисления или плана видов характеристик используется унарная конструкция `ЗНАЧЕНИЕ(Справочник.ИмяСправочника.ИмяПредопределенного)`. Данная конструкция вычисляется на этапе компиляции запроса самой платформой, а не СУБД. Если разработчик ошибается в имени предопределенного элемента, платформа выдает синтаксическую ошибку еще на этапе проверки кода, предотвращая Runtime-сбои в базе данных. Конструкция возвращает валидную ссылку (или пустую ссылку, если элемент был удален в режиме Предприятие, но остался в метаданных).
* **Что проверяем на практике:** Напишем запрос с извлечением ссылки на предопределенный элемент (или зафиксируем логику проверки через синтаксический анализатор пакетов) и докажем строгость контроля типов со стороны платформы 1С.


### Вопрос №1.13. Особенности ограничения длины строк неограниченной длины через функцию ВЫРАЗИТЬ() в запросах
* **Суть платформенного механизма:** В СУБД поля неограниченной длины (например, реквизиты справочников или документов с типом `Строка` и длиной `0`) хранятся в отдельных BLOB-таблицах. Из-за этого платформа запрещает использовать такие поля в операциях сравнения, группировки (`ГРУППИРОВАТЬ ПО`), сортировки (`УПОРЯДОЧИТЬ ПО`) и соединения таблиц. Конструкция `ВЫРАЗИТЬ(Поле КАК Строка(Н))` принудительно обрезает строку до фиксированной длины `Н` (не более 1024 символов) на уровне SQL-запроса. Это переводит поле в категорию строк фиксированной длины, позволяя СУБД корректно индексировать его и использовать в любых логических и группировочных операциях.
* **Что проверяем на практике:** Создадим пакетный запрос, который имитирует приведение строкового поля неограниченной длины к фиксированному типу через `ВЫРАЗИТЬ()`, фиксируя синтаксис обхода ограничений СУБД.

### Вопрос №1.14. Особенности явного и неявного сравнения полей типов Число и Строка в условиях запросов
* **Суть платформенного механизма:** В отличие от встроенного языка BSL, язык запросов 1С основан на строгой статической типизации SQL-серверов. В СУБД автоматическое (неявное) приведение типов при сравнении чисел со строками запрещено. Конструкция `ВЫРАЗИТЬ()` не поддерживает трансформацию типов `Строка -> Число` или `Число -> Строка` на уровне текста запроса. Единственный правильный способ сравнить числовое поле со строковым значением (или наоборот) — выполнить явное приведение типов на стороне встроенного языка BSL и передать в запрос готовое значение через механизм параметров (`УстановитьПараметр()`).
* **Что проверяем на практике:** Выполняем ошибочный запрос с прямым сравнением типов, перехватываем ошибку СУБД, а затем запускаем корректный вариант с предварительным приведением строкового значения к числу в BSL и передачей его через параметр запроса.

### Вопрос №1.15. Особенности использования логического оператора ПОДОБНО при поиске спецсимволов в запросах
* **Суть платформенного механизма:** Оператор `ПОДОБНО` в языке запросов 1С используется для маскирования и поиска подстрок. По умолчанию символы `%` (любая последовательность), `_` (один любой символ) и `[]` (диапазон) являются служебными метасимволами SQL. Если в текстовом поле базы данных физически записан символ процента или подчеркивания (например, артикул вида `ТОВ_15%`), прямой поиск через `ПОДОБНО "%_15%%"` отработает некорректно, так как СУБД воспримет эти знаки как маски. Для их экранирования платформа поддерживает специальное ключевое слово `СПЕЦСИМВОЛ "СимволЭкранирования"`. Символ, указанный после этого оператора, заставляет СУБД трактовать следующий за ним метасимвол как обычный текстовый знак.
* **Что проверяем на практике:** Создадим пакетный запрос, содержащий текстовую строку со спецсимволами (`%`), и продемонстрируем синтаксис точного поиска подстроки с использованием конструкции `СПЕЦСИМВОЛ`.


### Вопрос №1.16. Особенности работы оператора В ИЕРАРХИИ в условиях запросов
* **Суть платформенного механизма:** Оператор `В ИЕРАРХИИ` в языке запросов 1С предназначен для проверки принадлежности элемента к определенной группе итеративно вверх по дереву метаданных (для иерархических справочников). На уровне СУБД этот оператор транслируется платформой в рекурсивные подзапросы (или конструкции `UNION ALL` / общие табличные выражения `CTE` в зависимости от версии SQL). Важная особенность: если в качестве параметра передана пустая ссылка или пустой массив, СУБД выполняет избыточную работу, пытаясь построить дерево иерархии для пустых значений. Передача некорректных типов или больших неупорядоченных списков групп в этот оператор критически снижает скорость выполнения запроса.
* **Что проверяем на практике:** Создадим пакетный запрос с использованием конструкции `В ИЕРАРХИИ` для проверки синтаксиса и зафиксируем платформенные особенности оптимизации рекурсивных выборок.


### Вопрос №1.17. Особенности трансляции оператора В при передаче массивов большого объема в параметры запроса
* **Суть платформенного механизма:** Когда в условие запроса `ГДЕ Поле В (&МассивПараметров)` передается список значений или массив, платформа 1С осуществляет автоматическую конвертацию. При небольшом размере массива (обычно до нескольких сотен элементов) платформа транслирует его в обычное перечисление SQL-команды `IN (значение1, значение2, ...)`. Однако, если размер массива превышает внутренний порог оптимизатора платформы, 1С автоматически преобразует этот массив во временную таблицу на уровне СУБД и заменяет условие на неявное соединение таблиц (`EXISTS` или `JOIN`). Это предотвращает переполнение длины текста SQL-запроса и защищает от падения производительности из-за ограничений синтаксического анализатора СУБД.
* **Что проверяем на практике:** Сформируем массив большого объема, передадим его в параметр оператора `В` и проверим корректность обработки платформой тяжелого списка значений.

## Глава №2. Работа с регистрами и блокировками

### Вопрос №2.01. Автоматический и управляемый режимы блокировок данных в транзакции
* **Суть платформенного механизма:** В управляемом режиме блокировок платформа использует уровень изоляции СУБД Read Committed. Вся логическая изоляция данных (блокировка от чтения грязных данных другими транзакциями при проведении) перекладывается на сервер приложений 1С с помощью объекта `БлокировкаДанных`. Блокировка накладывается строго внутри транзакции и защищает выбранный диапазон данных (например, конкретный склад или товар) от параллельного изменения другими сеансами до окончания транзакции.
* **Что проверяем на практике:** Инициализируем объект `БлокировкаДанных` для справочника «Номенклатура», устанавливаем пространство блокировки по пустой ссылке и проверяем корректность вызова метода `Заблокировать()`.


### Вопрос №2.02. Разница между Исключительным и Разделяемым режимами управляемых блокировок
* **Суть платформенного механизма:** Разделяемая блокировка (Shared) накладывается при чтении данных и совместима с другими разделяемыми блокировками, позволяя параллельным транзакциям одновременно читать те же записи. Исключительная блокировка (Exclusive) накладывается при модификации данных, является абсолютно несовместимой с любыми другими блокировками и заставляет другие транзакции ожидать своей фиксации или отмены.
* **Что проверяем на практике:** Инициализируем последовательное наложение двух разделяемых блокировок на один и тот же элемент метаданных для подтверждения их совместимости, после чего проверяем логику конфликта с исключительным режимом.

### Вопрос №2.03. Место исполнения и хранения управляемых блокировок в архитектуре 1С
* **Суть платформенного механизма:** Управляемые блокировки данных (`БлокировкаДанных`) устанавливаются и проверяются исключительно средствами сервера приложений 1С:Предприятие (в памяти менеджера кластера). СУБД в управляемом режиме выполняет запросы на уровне изоляции `Read Committed` и не участвует в анализе совместимости логических пространств блокировок 1С. Объект `БлокировкаДанных` недоступен на клиенте и требует обязательного контекста транзакции на сервере.
* **Что проверяем на практике:** Реализуем вызов проверки контекста выполнения и перехватываем системное ограничение платформы при анализе доступности типов данных, фиксируя чисто серверную природу транзакционных блокировок.

### Вопрос №2.04. Поведение управляемой блокировки при захвате несуществующих записей (предотвращение фантомного чтения)
* **Суть платформенного механизма:** В управляемом режиме объект `БлокировкаДанных` осуществляет блокирование не физических строк в таблицах СУБД, а логических пространств в оперативной памяти сервера приложений 1С. Это позволяет успешно накладывать блокировки на несуществующие в базе данных записи (например, по свободным комбинациям измерений регистров или незанятым UUID), предотвращая фантомное чтение и запись со стороны параллельных транзакций без избыточного блокирования физических индексов SQL.
* **Что проверяем на практике:** Накладываем исключительную управляемую блокировку по сформированному в памяти случайному уникальному идентификатору (UUID), которого заведомо нет в таблицах СУБД, подтверждая валидность логического блокирования платформы.

### Вопрос №2.05. Механизм «Разделения итогов» регистров накопления и его влияние на блокировки
* **Суть платформенного механизма:** Режим разделения итогов регистров накопления предназначен для повышения параллельности работы пользователей при одновременной записи движений. При включенном режиме платформа распределяет актуальные итоги по нескольким физическим строкам СУБД с использованием внутреннего разделителя. Это позволяет параллельным транзакциям изменять остатки по одинаковым комбинациям измерений без взаимного блокирования, снижая вероятность таймаутов и эскалации блокировок таблиц.
* **Что проверяем на практике:** Проверяем логику обращения к свойствам метаданных регистров и фиксируем базовые системные константы управления разделением таблиц остатков на уровне сервера приложений.


### Вопрос №2.06. Поведение транзакции при превышении времени ожидания блокировки данных (Таймаут СУБД)
* **Суть платформенного механизма:** Если транзакция запрашивает данные, монопольно занятые другим сеансом, она переходит в режим ожидания. При превышении установленного лимита времени (таймаута) платформа 1С прерывает операцию и генерирует Runtime-исключение «Превышено максимальное время ожидания предоставления блокировки». Данный сбой переводит текущую транзакцию в состояние краха и инициирует её автоматический полный откат СУБД.
* **Что проверяем на практике:** Программно имитируем перехват системной ошибки таймаута блокировки данных через блок исключений, подтверждая логику безусловного отката транзакционных пакетов платформы при конфликтах параллельного доступа.


### Вопрос №2.07. Автоматическое выставление управляемой блокировки через БлокироватьДляИзменения у движений регистров
* **Суть платформенного механизма:** Установка свойства `БлокироватьДляИзменения` в значение `Истина` у набора записей регистра накопления или регистра бухгалтерии заставляет платформу автоматически сформировать и наложить управляемую исключительную блокировку по комбинациям измерений, присутствующим в данном наборе. Это блокирует параллельные транзакции от модификации данных остатков по этим аналитикам на время проведения документа, защищая алгоритмы контроля отрицательных остатков от некорректного срабатывания («состояния гонки»).
* **Что проверяем на практике:** Фиксируем корректный синтаксис обращения к транзакционному свойству `БлокироватьДляИзменения` наборов записей, обеспечивающему автоматическую генерацию пространств логических исключительных блокировок.


### Вопрос №2.08. Особенности работы механизмов Последовательностей документов при параллельном проведении
* **Суть платформенного механизма:** Механизм Последовательностей документов использует в СУБД общую таблицу Границ Последовательности. При параллельном проведении документов множеством пользователей запись в таблицу границ становится критической точкой конкуренции (точкой эскалации блокировок). Для минимизации таймаутов на больших нагрузках разработчик должен разделять последовательности по измерениям (например, по Организациям) либо выносить сдвиг границы из оперативного проведения транзакции документа в фоновые регламентные задания.
* **Что проверяем на практике:** Фиксируем программную структуру работы с менеджерами последовательностей и особенности управления границами документов для прохождения тестов оптимизации системной хронологии.


### Вопрос №2.09. Разница между Периодическими и Непериодическими регистрами сведений в СУБД (Формирование уникального ключа записи)
* **Суть платформенного механизма:** Уникальность записей регистра сведений в СУБД контролируется через первичный ключ. В непериодическом регистре ключ уникальности состоит строго из совокупности всех его Измерений. В периодическом регистре платформа принудительно включает поле `Период` в состав уникального ключа, что позволяет хранить хронологические срезы данных по одинаковым измерениям.
* **Что проверяем на практике:** Фиксируем логическую структуру построения ключей записи и индексов для различных типов регистров сведений в соответствии со стандартами тестирования «1С:Профессионал».

### Вопрос №2.10. Влияние свойства «Основной отбор» на автоматическую индексацию таблиц в регистрах сведений
* **Суть платформенного механизма:** Свойство `Основной отбор` у измерений регистра сведений управляет созданием дополнительных индексов в СУБД. Включение этого признака заставляет платформу автоматически сгенерировать некластерный индекс по данному измерению. Это кардинально ускоряет выполнение запросов с фильтрацией по этому полю, переводя операции СУБД из режима сканирования таблицы (Table Scan) в режим быстрого поиска по индексу (Index Seek), а также повышает параллельность работы за счет точечного наложения блокировок.
* **Что проверяем на практике:** Фиксируем логику работы оптимизатора индексов СУБД для регистров сведений в соответствии со спецификацией вопросов экзамена «1С:Профессионал».


### Вопрос №2.11. Особенности работы механизма ОбменДанными.Загрузка = Истина при записи регистров
* **Суть платформенного механизма:** Свойство `ОбменДанными.Загрузка = Истина` используется для отключения прикладной логики и автоматических проверок платформы при выполнении обмена данными. Этот режим блокирует стандартные контроли (например, контроль уникальности номеров документов), но не отключает ограничения на уровне СУБД (уникальность физических индексов таблиц). В коде обработчиков событий модулей объектов разработчик обязан явно анализировать этот флаг для предотвращения выполнения тяжелых алгоритмов проверки остатков при загрузке.
* **Что проверяем на практике:** Фиксируем программную логику анализа транзакционного признака `ОбменДанными.Загрузка` для корректного прохождения тестов по механизмам синхронизации и обмена данными.


### Вопрос №2.12. Логика работы виртуальной таблицы Обороты при наличии незакрытых остатков в СУБД
* **Суть платформенного механизма:** Виртуальная таблица `Обороты` регистра накопления (даже для регистров вида Остатки) при вычислении данных обращается исключительно к физической таблице Движений СУБД. Платформа полностью игнорирует таблицу Итогов при формировании оборотных данных. Как следствие, наличие некорректных, незакрытых или «зависших» остатков по измерениям регистра никак не влияет на точность результатов выборки оборотов за указанный период.
* **Что проверяем на практике:** Фиксируем архитектурные правила расчета виртуальных оборотных таблиц 1С для успешного прохождения специализированных тестов экзамена «1С:Профессионал».

### Вопрос №2.13. Разница между физическими таблицами Движений и Итогов в регистрах накопления при расчете остатков
* **Суть платформенного механизма:** Расчет остатков на произвольную дату выполняется платформой комбинированно: СУБД считывает базовую опорную точку из таблицы Итогов (ближайшее начало месяца) и докручивает разницу (плюс или минус) по детальным записям из таблицы Движений за промежуточный отрезок времени. Таблица Итогов хранит рассчитанные данные по умолчанию на начало каждого месяца, а максимальная точка рассчитанных периодов определяет текущую Границу итогов регистра.
* **Что проверяем на практике:** Фиксируем архитектурные правила взаимодействия физических таблиц остатков для сдачи специализированных вопросов экзамена «1С:Профессионал».
