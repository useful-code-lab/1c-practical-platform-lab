### Вопрос №1.01. Проверка пустой ссылки через функцию ЗначениеЗаполнено()
* **Суть платформенного механизма:** В платформе 1С пустая ссылка (например, `Справочники.Номенклатура.ПустаяСсылка()`) — это не `Неопределено` и не `Null`. Это полноценное валидное значение ссылочного типа, состоящее из нулевого уникального идентификатора (00000000-0000-0000-0000-000000000000). Системная функция `ЗначениеЗаполнено()` спроектирована так, что она распознает пустую ссылку любого типа и возвращает для неё `Ложь`.
* **Что проверяем на практике:** Проверяем пустую ссылку справочника с помощью `ЗначениеЗаполнено()`, а также сравниваем её с `Неопределено`, чтобы зафиксировать разницу в поведении системы.

### Вопрос №1.02. Поведение значений NULL при логических операциях сравнения в запросах
* **Суть платформенного механизма:** В языке запросов 1С:Предприятия значение `NULL` подчиняется правилам трехзначной логики SQL (истинного отсутствия данных). Любое прямое сравнение значения `NULL` с помощью стандартных математических операторов (`=`, `<>`, `<`, `>`), даже с самим собой (`NULL = NULL`), принципиально возвращает результат `Ложь` (точнее, `Unknown`, который трактуется как `Ложь`). Для корректного определения пустого SQL-поля (например, при левом соединении) платформа требует использовать специализированный унарный оператор `ЕСТЬ NULL`.
* **Что проверяем на практике:** Выполняем SQL-запрос к справочнику, вычисляя выражения `NULL = NULL` и `NULL ЕСТЬ NULL` внутри конструкции `ВЫБОР`. Доказываем разницу в логике СУБД.


### Вопрос №1.03. Особенности неявного приведения типов при сложении в языке BSL
* **Суть платформенного механизма:** В программном коде 1С тип результирующего выражения при использовании оператора сложения `+` жестко определяется типом **первого (левого)** операнда. Если левый операнд имеет тип `Строка`, платформа выполняет конкатенацию, приводя правый операнд к строке. Если левый операнд имеет тип `Число`, платформа пытается выполнить математическое сложение, принудительно преобразуя правый операнд к числу. Если правая строка содержит нецифровые символы, система генерирует неустранимое исключение времени выполнения (Runtime Error) «Преобразование значения к типу Число не может быть выполнено».
* **Что проверяем на практике:** Поочередно складываем строку с числом и число со строкой (включая невалидную текстовую строку), перехватывая системную ошибку типизации через блок `Попытка...Исключение`.


### Вопрос №1.04. Особенности типизации и логика «Пустой ссылки» составного типа в запросах
* **Суть платформенного механизма:** Когда реквизит имеет составной тип, СУБД хранит его в нескольких физических полях: поле «Тип» и поле «Идентификатор». Если реквизит не заполнен, его значение в базе равно специальной пустой ссылке конкретного типа (или `Неопределено`, если тип еще не выбран). В языке запросов 1С конструкция `Реквизит ЕСТЬ NULL` вернет `Ложь` для незаполненного составного поля, потому что там физически лежит пустая ссылка, а не `NULL`. Чтобы проверить составное поле на «пустоту» в запросе, нужно использовать конструкцию `Реквизит = ЗНАЧЕНИЕ(Справочник.ИмяСправочника.ПустаяСсылка)`.
* **Что проверяем на практике:** Добавим в нашу обработку запрос, который проверяет незаполненный реквизит составного типа. Сравним поведение условий `ЕСТЬ NULL` и `= ЗНАЧЕНИЕ(...)`, чтобы наглядно увидеть разницу.


### Вопрос №1.05. Поведение виртуальных таблиц при использовании условий ГДЕ вместо параметров
* **Суть платформенного механизма:** При работе с виртуальными таблицами (например, `СрезПоследних`, `Обороты`) платформа 1С генерирует подзапросы к СУБД. Если условие (например, по номенклатуре) передано в параметры самой виртуальной таблицы, платформа накладывает фильтр на самом раннем этапе выборки данных в подзапросе СУБД. Если же фильтр наложен в секции `ГДЕ` итогового запроса, СУБД сначала выберет абсолютно все записи из базы (вычислит итоги или срез для терабайта данных), построит огромную временную таблицу и только потом отсечет лишнее. Это приводит к критическому падению производительности и избыточной нагрузке на дисковую подсистему и память.
* **Что проверяем на практике:** Напишем два запроса к несуществующему регистру (или сымитируем обращение через синтаксический анализ), чтобы зафиксировать правильный синтаксис передачи параметров фильтрации вглубь виртуальной таблицы.


### Вопрос №1.06. Разница между ссылочными и объектными типами при изменении данных в базе
* **Суть платформенного механизма:** В 1С важно разделять легковесные ссылки (`СправочникСсылка`) и тяжелые объектные типы (`СправочникОбъект`). Ссылка — это просто UUID, она не хранит в себе данные реквизитов и не блокирует базу. Чтобы изменить данные, необходимо получить объект методом `ПолучитьОбъект()`, который считывает всю запись из СУБД в память и накладывает оптимистическую (или пессимистическую) блокировку. Запись данных всегда происходит только через объект методом `Записать()`. Попытка изменить реквизит напрямую у ссылки вызовет ошибку компиляции или выполнения, так как ссылка доступна только для чтения.
* **Что проверяем на практике:** Попробуем программно изменить реквизит у ссылки, перехватим ошибку платформы через блок `Попытка...Исключение` и покажем правильный способ модификации данных через получение объекта.


### Вопрос №1.07. Поведение транзакций при использовании оператора Попытка...Исключение
* **Суть платформенного механизма:** В платформе 1С любая ошибка уровня СУБД (например, нарушение уникальности индексов базы данных) внутри транзакции безвозвратно переводит её в состояние сбоя (Transaction Doomed). Конструкция `Попытка...Исключение` в коде BSL позволяет перехватить эту ошибку, чтобы сеанс пользователя не завершился аварийно, но она **не способна спасти транзакцию**. Блокировка и состояние сбоя фиксируются на уровне СУБД. Любая последующая попытка вызвать `ЗафиксироватьТранзакцию()` гарантированно вызовет критическое исключение: «Транзакция активна, но её выполнение невозможно».
* **Что проверяем на практике:** Открываем транзакцию и внутри блока `Попытка` намеренно создаем два элемента справочника с одинаковым кодом, вызывая ошибку уникальности СУБД. Перехватываем её и доказываем, что транзакцию после этого зафиксировать уже невозможно.


### Вопрос №1.08. Поведение параметров ЗаполнитьЗначенияСвойств() при несовпадении типов
* **Суть платформенного механизма:** Встроенная функция `ЗаполнитьЗначенияСвойств()` осуществляет копирование данных между реквизитами разных объектов по совпадению их имён. Однако, если имена свойств совпадают, но их типы принципиально различны (например, в источнике лежит `Строка`, а в приемнике — `Число`), платформа производит попытку неявного приведения типов. Если приведение невозможно, система не генерирует ошибку времени выполнения (Runtime Error) и не прерывает код, а просто тихо игнорирует данное свойство, оставляя значение в приемнике неизменным. Это поведение критически важно учитывать при написании универсальных механизмов обмена данными, чтобы не допускать скрытой потери данных.
* **Что проверяем на практике:** Создадим структуру-источник со свойством типа `Строка` и структуру-приемник с таким же именем свойства, но типа `Число`. Выполним копирование и зафиксируем, как платформа предотвращает аварийное завершение потока и сохраняет исходное значение приемника.

### Вопрос №1.09. Поведение индексов во временных таблицах при оптимизации сложных запросов
* **Суть платформенного механизма:** Когда в запросе создается временная таблица (`ПОМЕСТИТЬ ВТ_Данные`), СУБД физически создает реальную таблицу в базе данных `tempdb`. Если эта таблица в дальнейшем соединяется с другими таблицами по определенным полям (например, по ссылке), СУБД вынуждена выполнять полное сканирование (`Table Scan`), что критически снижает скорость при объемах более нескольких сотен строк. Конструкция `ИНДЕКСИРОВАТЬ ПО Поле` принудительно создает индекс в СУБД для этой временной таблицы. Это позволяет оптимизатору использовать высокоскоростной поиск (`Index Seek`) вместо сканирования, сокращая время выполнения запроса в десятки раз.
* **Что проверяем на практике:** Создадим пакетный запрос с временной таблицей, содержащей индексацию, и зафиксируем синтаксическую корректность конструкции для оптимизации планов запросов СУБД.

### Вопрос №1.10. Разница между методами Прочитать() и ПолучитьОбъект() при оптимизации памяти
* **Суть платформенного механизма:** Когда необходимо обновить данные уже существующего в памяти объекта (`СправочникОбъект`), вызов метода `Ссылка.ПолучитьОбъект()` заставляет платформу уничтожить старый объект, выделить память под новый экземпляр, повторно считать все реквизиты из СУБД и заново инициализировать механизмы блокировки. Специализированный метод `Объект.Прочитать()` работает иначе: он не пересоздает объект в памяти, а просто обновляет значения его текущих реквизитов напрямую из базы данных. Это исключает лишние аллокации в оперативной памяти и снижает нагрузку на сборщик мусора.
* **Что проверяем на практике:** Создадим элемент справочника, изменим его свойства в памяти и поочередно применим оба метода. Через операторы сравнения докажем, что `ПолучитьОбъект()` создает новый объект в памяти, а `Прочитать()` обновляет текущий.
